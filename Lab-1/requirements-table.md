# Requirements Table

Feature Flag & Dynamic Config Manager (Problem Statement #43)

Gnanasagar H, PES1UG24CS171, Section 5 - 'C'

| Req ID | Type | Description | Priority | Acceptance Criteria | Rationale | Comments (peer critique) |
|---|---|---|---|---|---|---|
| FR-001 | Functional | The system shall evaluate user targeting rules (User ID hash, Beta cohort) and return the correct boolean state of a feature flag for that user. | High | Pass: with a 10% rollout, every user whose ID hash falls in the 10% bucket gets true. Fail: any user outside the cohort gets true. | This is the main job of the platform. If evaluation is wrong, the wrong users see unreleased features. | Peer: say how users are bucketed so results repeat. Revised: evaluation uses the User ID hash bucket; FR-002's test checks it stays stable. |
| FR-002 | Functional | The system shall let a Release Manager set a percentage rollout (0 to 100, in steps of 1%) for a flag in a chosen environment. | High | Pass: setting 25% on 10,000 test user IDs enables the flag for 2,500 users (within +/- 1%), and the same user gets the same result on repeated calls. Fail: values outside 0 to 100 are accepted, or a user's result changes between calls. | Gradual rollout lets the team limit the impact of a bad release to a small group of users. | Peer: "gradual" was vague. Revised: added the 0 to 100 range, 1% steps and a 10,000-user test with +/- 1% tolerance. |
| FR-003 | Functional | The system shall allow a Software Engineer to set an environment override so that a flag can hold different values in development, staging and production. | High | Pass: turning a flag on in staging leaves its production value unchanged, and SDKs in each environment read their own value. Fail: a change in one environment shows up in another. | Engineers need to test a feature in staging without exposing it to real users. | Peer: name the environments. Revised: development, staging and production listed. |
| FR-004 | Functional | The system shall push flag and config changes to all connected client SDKs within 5 seconds of the change being saved. | Medium | Pass: in a test with 1,000 connected SDK clients, all of them report the new value within 5 s of the save. Fail: any client still has the old value after 5 s. | Real-time sync means a broken feature can be switched off quickly, without a redeploy. | Peer: "real time" is not testable. Revised: set a 5 s limit and a 1,000-client test. |
| FR-005 | Functional | The system shall record every flag change (who, when, environment, old value, new value) in an audit log and let a Release Manager roll a flag back to any earlier version. | Medium | Pass: each change appears in the log with all five fields, and choosing a past version restores that exact value. Fail: a change is missing from the log or the rollback restores a different value. | The team needs to know who changed what during an incident and undo it fast. | Peer: list what the log stores. Revised: five fields named, rollback check added. |
| NFR-001 | Nonfunctional (Performance & Security) | The flag evaluation API shall respond in under 15 ms (p99) under simulated peak load, and accept only authenticated requests over TLS 1.2 or higher. | High | Pass: a load test at 5,000 requests/s shows p99 latency below 15 ms, and requests without a valid SDK key or over plain HTTP are rejected. Fail: p99 at or above 15 ms, or an unauthenticated request succeeds. | Evaluation runs inside the client's critical path, so it has to be fast. Flag data can reveal unreleased features, so it must be protected. | Peer: "security standards" was unclear. Revised: TLS 1.2+, SDK key check, and a 5,000 requests/s load figure. |
| NFR-002 | Nonfunctional (Reliability) | The system shall be available 99.9% of each month, and client SDKs shall keep serving the last known flag values if the service cannot be reached. | High | Pass: monthly uptime report shows at least 99.9%, and with the server stopped, an SDK keeps returning its cached values with no errors to the host app. Fail: uptime below 99.9%, or the SDK throws or returns default values during the outage. | Customer apps depend on the flag service at runtime. An outage here should not take their apps down too. | Peer: what happens to clients during an outage? Revised: SDK must keep serving cached values. |

FR-001 and NFR-001 are adapted from the samples in the problem statement.
